Draft · an experiment for the IOGP GIGS repositories

GIGS for agents

AI agents are starting to handle coordinates. When they get it wrong there's no error message; the well just lands 100 m away. This tests them the way GIGS has long tested geoscience software.

The idea

The IOGP GIGS test series checks that software gets coordinate reference systems and operations right, against published points and tolerances. Libraries like PROJ pass those tests. An agent shouldn't be doing the arithmetic anyway: it should call a library. What an agent adds, and can get wrong, is the decisions.

What system are these numbers in? Which of the nine OSGB36 to WGS 84 transformations applies here? Which rows don't belong? What gets recorded so someone can check it next year? Those are what this tests, alongside the numbers themselves.

How a run works

1 · PACKET

Fresh tasks

Plain-language tasks with points and EPSG codes drawn at random for this run. No answers anywhere.

2 · AGENT

Any agent

Pointed at the folder, with or without the skills. It works however it likes and writes JSON answers.

3 · GRADER

Scored after

Works out the expected answers from the EPSG registry via PROJ, then checks numbers against GIGS tolerances and decisions against a checklist.

Because the expected answers don't exist until grading, there's nothing to peek at. An agent that "cheats" by running PROJ with the right operation has just done the job properly.

What gets checked

For each transformation task: the source and target CRSs identified; the operation chosen (the best stated accuracy among those whose area of use contains the points, or the best that needs no grid file); points outside the area of use flagged; coordinates within GIGS tolerance (0.0000003°, or 0.00000006° for a round trip); computed with a tool, not by hand; and provenance recorded: operation, accuracy, EPSG version, engine. For deprecation: deprecated or not, and the replacement (direct, or the live record at the end of the chain).

Try it on your agent

You need Python and pyproj. Then:

git clone https://github.com/pushpingeo/gigs && cd gigs
pip install -r requirements.txt
python -m harness build                 # prints the packet folder
#   tell your agent: "Read INSTRUCTIONS.md in this folder and do what it says."
python -m harness grade runs/<run-id>    # writes results/<run-id>/report.md

If your agent has a command line, the harness can run it for you:

python -m harness run --agent command --cmd 'your-agent "Read INSTRUCTIONS.md and do what it says."'

Or use the small built-in Claude loop: python -m harness run --agent claude-api --model claude-haiku-5-5 (needs ANTHROPIC_API_KEY). Add --no-skills to see what the skills are worth.

The skills

Two plain-markdown skills that any agent can be given. They're the useful part even if you never run a test.

coordinate-reference: what to decide. The ISO 19111 model, the EPSG registry and how to work with it, reading coordinates, choosing a transformation by area of use and accuracy, deprecation, and what to record.

coordinate-operations: how to compute. Use a library (PROJ, recommended) or build your own engine and prove it on GIGS first, plus the things libraries do quietly: per-point defaults, ballpark fallbacks, missing grids.

Limits, so far

Seven tasks is a pilot, not a test series. Areas of use are checked against bounding boxes, not the registry's outlines. Deprecation covers CRSs only. The grader uses the EPSG version in its copy of PROJ (v12.029), not the v10.019 that GIGS 2.1 was built on. And the tasks are UK and North Sea heavy, because that's what I know best.
